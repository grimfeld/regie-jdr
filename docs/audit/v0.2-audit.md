### Behavioural / design issues

1. **No "prepare vs live" separation.** Every keystroke in the title/description inputs and every thumbnail click goes straight to the broadcast window (`App.tsx:39-42`). The GM cannot prepare anything without revealing it — this violates the core no-spoiler requirement.
2. **Preview ≠ broadcast.** Preview is a fixed 16:9 box with `object-fit: cover`; the stage is `cover` on whatever the window aspect is. Crops differ as soon as the stage window is not 16:9.
3. **Broadcast window is not clean.** It renders a fullscreen button (`⛶`) and a "SCÈNE EN COURS" caption that Discord viewers will see.
4. **Theme bleeds into the broadcast.** The stage uses `var(--accent2)` and always gets the default `imperium` theme (theme state is per-window, not synced).
5. **Asset library vanishes on restart.** Files persist in `userData/assets`, but nothing indexes them; they become orphans. Re-importing the same file duplicates it (UUID names, no hashing) — unbounded growth.
6. **Single-monitor concerns (unverified):** Chromium throttles background/occluded windows and, on Windows, native occlusion tracking can stop painting a covered window. A broadcast window hidden behind the GM window may freeze in the Discord stream. Minimized windows are not captured by Discord at all.

### Technical debt

- `App.tsx` is a single component holding both views, all state, and all UI.
- `styles.css` is minified one-line CSS — unreviewable, unmergeable.
- IPC is untyped (`unknown` payloads, duplicated `ImportedAsset` type in 3 places), unvalidated, and both windows get the same full API (the broadcast window can import files and push scenes).
- No CSP, no navigation/`window.open` guards, no single-instance lock.
- `body { min-width: 980px }` applies to the broadcast window too.
- No tests, no lint/format config, no CI, no git hooks.

## B. Architecture Assessment

**Verdict: keep the stack.** Electron + React + TypeScript + Vite is appropriate for an offline Windows desktop tool with two windows, local media, and Web Audio. No rewrite is warranted; the prototype is small enough to restructure incrementally.

### Electron security — upgrade and harden (tangible benefit: patched Chromium, least privilege)

- Upgrade to a supported Electron major (first P0 action after the build fix).
- Explicit `sandbox: true`; deny `window.open` (`setWindowOpenHandler`) and off-origin navigation (`will-navigate`); add a CSP meta tag allowing only `self` and `regie-asset:`.
- **Two preload scripts / two API surfaces:** the broadcast window gets read-only subscribe + `getState`; only the control window can import, mutate, or toggle.
- Validate the IPC sender (`event.senderFrame`, window identity) and payload shape in main. Hand-written type guards are enough for now; adopt a schema library only if contracts grow large.
- `app.requestSingleInstanceLock()`; Electron fuses (disable `RunAsNode`, etc.) at packaging time.

### Local asset handling — keep the custom protocol, add content addressing

- `regie-asset://` is the right approach (works in dev and prod, no `file://` exposure, path-traversal guarded). Keep it.
- Store files per Campaign as `campaigns/<id>/media/<sha256>.<ext>` → deduplication within a Campaign; the same file imported into two Campaigns is copied twice (accepted, keeps export/delete trivial).
- Index metadata (id, hash, original name, kind, tags, dimensions/duration, campaign) in the persistence layer.
- Handler returns `404` for missing files; renderer shows a "missing media" placeholder and offers relink.
- Allowlist extensions/MIME types; set `Content-Type` explicitly.

### Scene rendering — one renderer, fixed logical canvas

- A single `<StageRenderer state={...}>` component used by **both** the preview and the broadcast window.
- Render into a fixed logical canvas (1920×1080) scaled with CSS `transform` and letterboxed. Store all positions/sizes **normalized (0–1)** relative to that canvas. Result: preview and broadcast are pixel-identical at any window size.
- DOM + CSS transitions (opacity/transform) are sufficient for backgrounds + a handful of character layers. Canvas/WebGL is not justified.

### State management — main process owns the on-air state

- Main process holds the authoritative **on-air state**: the open Campaign and its Active Scene (with a monotonically increasing `version`). Renderers send typed *commands*; main validates, applies, persists, and broadcasts the full snapshot.
- Broadcast window **pulls** the snapshot on mount (`invoke('show:get')`) then subscribes — fixes B3 and makes reopen/reload trivially correct. Snapshots are small (IDs + transforms), so sending the whole state is simpler than diffing.
- No draft/Take: editing the Active Scene changes the broadcast immediately and is saved into the Scene. Preparation stays private because every other Scene is off air. Activating a Scene puts it on air.
- Renderer state: a small store with `useSyncExternalStore`. No Redux/Zustand needed at this size; revisit if it hurts.

### Audio routing & Discord — the biggest unknown; spike it first

Facts and constraints:

- Discord's Windows "share application window with audio" captures audio per application/process, not per window. Discord does not document its implementation. Third-party tools that mimic it use Windows process-loopback capture ([application-loopback](https://github.com/WerdoxDev/application-loopback)). Chromium/Electron play all audio through one audio-service process under the app's main process. **Expected (unverified):** sharing the broadcast window captures *all* audio the app plays, from either window. Corollaries:
  - Any GM-only "pre-listen" sound would also reach players unless played through a different device.
  - Independent local vs broadcast volume is **impossible** with application capture alone — there is one stream.
- **Where audio lives:** put the audio engine in the **control window** (or a hidden dedicated window), not the broadcast window, so closing/reloading the broadcast never cuts the music. If the spike shows Discord only captures the shared window's own renderer, move the engine into the broadcast window and drive it via IPC.
- **Engine:** Web Audio API with `HTMLAudioElement` → `MediaElementAudioSourceNode` (streams long tracks) → per-bus `GainNode`s (music, ambience, sfx, master). This gives sample-accurate fades/crossfades with `linearRampToValueAtTime`. Howler.js adds little on top of this and hides the graph; **recommend removing it** unless the spike reveals a need.
- **Separate local/broadcast mix (P2, optional):** Chromium supports `AudioContext.setSinkId()`. Two contexts → speakers (GM monitor) + a virtual cable (e.g. VB-Audio Cable). Trade-off: players then hear audio via Discord's *microphone* input set to the cable, which conflicts with the GM's real microphone (needs a mixer such as Voicemeeter), adds latency, needs a third-party driver, and is fiddly to support. Only worth it if the GM genuinely needs different levels.
- Remove the "Écoute MJ / Diffusion" sliders until something real is behind them.

### Persistent storage — JSON per campaign now, SQLite later if needed

- Data volume is small (tens of scenes, hundreds to low thousands of media records per campaign). Recommend **JSON documents per campaign** (`campaigns/<id>/campaign.json`, `scenes.json`, `library.json`) written atomically (temp file + rename), with a `schemaVersion` and a migration function. Benefits: zero dependencies, no native module rebuilds for packaging, human-readable, campaign export = zip the folder.
- Keep it behind a small repository interface so a move to SQLite (`node:sqlite` built into recent Node/Electron, avoiding `better-sqlite3` native rebuild pain) is local if search/tagging at scale demands it.
- Binary media stays on the filesystem (content-addressed), never in the database.
- Campaigns are in the MVP: the home page is the Campaign list (skipped when exactly one Campaign exists); there is no implicit Default Campaign.

### Proposed structure (incremental, not a big-bang move)

```
electron/
  main.ts            app lifecycle only
  windows.ts         control/broadcast window creation + hardening
  ipc/               typed channel contracts + handlers + validation
  assets/            protocol handler, import, hashing
  storage/           JSON repository, atomic writes, migrations
  on-air-state.ts    authoritative on-air state
  preload-control.ts / preload-broadcast.ts
src/
  shared/            types shared with electron (domain models, IPC contract)
  features/{stage,library,scenes,audio,soundboard,themes,settings}/
  components/ui/
```

## D. Implementation Roadmap

1. **Make it ship (days 1–2):** F-01 → F-02 → F-03, plus SPIKE-01 by the user in parallel as soon as F-01 lands.
2. **Contracts & data (days 3–6):** F-04 → F-05 → F-06, F-07 → F-08 → F-09, F-10, then F-11 (packaging check while the foundation is fresh).
3. **Visual MVP (week 2):** V-01 first (everything renders through it), then V-02, V-03, V-04, V-05, V-06, V-07.
4. **Audio MVP (week 3):** A-01 per ADR-0002 → A-02 → A-03, A-04 → A-05 → A-06.
5. **Scenes (week 3–4):** S-01 → S-02 → S-03. **MVP reached.** Run a full mock session with the manual checklist.
6. Then C-* (campaigns) → T-* (themes) → B-* → Q-*.

Rationale: the spike is the only item that can force an architectural change (where audio lives, how the broadcast window must behave on one monitor), so it runs first and in parallel. Visual work precedes audio because the shared renderer and on-air state are prerequisites for scenes, and scenes need both.

## E. First Implementation Proposal

Implement **F-01 (production build fix)**, **F-02 (Electron upgrade + security baseline)**, and **F-03 (tests + CI)** as one small first slice, and have the user run **SPIKE-01** right after F-01.

Why:
- F-01 is a confirmed, one-line, release-blocking bug: today every non-dev launch is a blank window, which also makes packaging and the Discord spike impossible.
- F-02 must happen before writing more Electron code, because the API surface and defaults should be targeted against a supported version, not EOL 33.
- F-03 gives every later ticket a regression net (the F-01 smoke test is its first test) and keeps the minified stylesheet from accumulating more debt.
- SPIKE-01 is the highest-uncertainty item in the project; its answer decides the audio architecture, so it should not wait until week 3.

## Manual acceptance checklist (living)

**Single monitor, Windows 11**
- [ ] Control + broadcast windows open side by side; broadcast resizable to ~1/3 screen without layout breakage.
- [ ] Broadcast keeps updating while partially covered by the control window.
- [ ] Broadcast fullscreen toggle from the GM window, and back.
- [ ] Broadcast reopen restores the live scene instantly.

**Discord window share**
- [ ] Share the broadcast window (not the screen); remote viewer sees only scene content.
- [ ] Draft edits and hidden characters never appear on the stream.
- [ ] Stream does not freeze when the GM works in the control window.

**Audio**
- [ ] GM hears music and SFX locally.
- [ ] Remote listener hears music and SFX through the stream, in sync, without echo.
- [ ] Volume changes are audible on both ends.

**Sample session**
- [ ] Prepare 3 scenes before the session; restart the app; run forest → ambush (music crossfade, footsteps, branch break, enemy reveal) → aftermath, all from the control window in ≤2 clicks per action.
